# Preregistration: domain-conditioned mutation replay, development preflight (2026-11-10)

## Claim boundary and provenance

This is a **synthetic development preflight, NOT an external RSI audit**. Task IDs are pinned by `domain_policy_dev_manifest_20261110.json` in commit `9a1159519b3adf5126160b3069396c4ecd34beec`, separately and BEFORE any runner. The names are taken only from the existing TRAIN partition of upstream DreamCoder `ellisk42/ec` at `cb0e63f5c33cd2de360b791038b0f5272750270e`; source file blob `2816d1ee51ff2f523704c1930d8736eb99711036`, local split blob `afac5b3f2dc346027caaba36f308f2b1e078ebda`. The runner creates toy input/output instances from task-name semantics; these are **not independently frozen test examples**. Existing TEST/VALIDATION/J/RSI-4 and prior PR #50–58 audit tasks/checkpoints are excluded. No independent transfer or correctness claim is permitted.

## Fixed design, before any run

- 40 independent, paired seed trajectories, seeds 0..39; 3 generations.
- All 29 frozen TRAIN names; split by `sha256(name).digest()[0] % 3 == 0` into development-evaluation vs support, independently of performance.
- Six arms: `persistent_domain` (all support episodes replayed), `frozen_mutation` (unchanging deduplicated fixed candidate ordering), `no_memory` (fresh deduplicated uniform sampling), `wiped_each_generation` (only current-generation support episodes), `single_generation` (all three generations' support candidate budget consumed only at generation 3), and `inverted_feedback` (negative control, incorrectly rewards public failures).
- Fixed grammar of list transformations and scalar/list outputs specified in the runner; fixed candidate pool, **16 distinct candidate evaluations per task per evaluation checkpoint**. Each candidate receives 8 generated public inputs and 32 generated varied-size shifted inputs, even after public mismatch, to equalize calls. Only public correctness can train the controller; shifted results never enter its policy.
- Support training: 16 distinct candidate evaluations per support task per support pass, 8 public interpreter calls per candidate; 1 pass each generation except `single_generation` (0, 0, 3 passes). Evaluation: one 16-candidate pass per development-evaluation task per generation. All arms get equal **trajectory-total** support and evaluation candidate/VM counts, but `single_generation` intentionally has unequal per-checkpoint support budgets. Generator and interpreter CPU and wall time are measured and reported separately; equal call counts are **not** CPU parity.
- Policy: domain derived only from input/output types and public length behavior, not task names; a beta-smoothed success rate per operator family, fitted from public support episodes. Weighted Gumbel ranking chooses 16 unique candidate programs. Inverted-feedback uses `1-public_success` as reward.
- Success for this preflight only: public and all 32 synthetic shifted cases pass for at least one candidate. This is NOT externally verified task correctness. Spurious public-fit fraction and per-domain regressions must be reported.
- Seed-clustered paired bootstrap 2,000 resamples, percentile 95% CI. Pair each seed/task/generation against each baseline; report wins/losses/ties. Do not treat task × seed as independent replicates.

## Prospective quantitative predictions and gates

H1: At generation 3, persistent-domain exceeds **both** fixed and no-memory by >=5.0 percentage points in development-evaluation pass rate, with each seed-clustered paired 95% CI strictly above 0.0 pp. H2: Its paired improvement vs the stronger of those two controls grows strictly from generation 1 to 2 to 3, with no domain-level regression at generation 3. H3: Retention loss (tasks passed at generation 1 but failed at generation 3) is <=5.0% of evaluation task/seed pairs; `wiped_each_generation` is not allowed to be silently omitted. H4: inverted-feedback does not exceed both simple controls at generation 3. H5: trajectory-total candidate and actual interpreter calls are exactly equal across arms, and measured total CPU for each arm is within +/-10% of frozen mutation; if CPU parity fails, overall gate fails regardless of apparent solve gains. Per-checkpoint CPU mismatch for the intentionally front-loaded single-generation control is explicitly reported.

`preregistered_success` is the conjunction H1..H5. The preflight stops after the single fixed 40-seed run regardless of outcome. No gate changes, new candidate selection, or rerun after seeing results. Engineering exceptions before the first run may be corrected in a separate documented commit without changing hypotheses. The entire run is spent after first results. An external audit would require a **new, independent** manifest and separate preregistration.
