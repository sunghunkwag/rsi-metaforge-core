# Follow-up: improve the improvement procedure

This is a new development study, not a revision of the completed RSI-2 study.
The original predictions, configuration, split, raw measurements and null result
remain unchanged. No original TEST outcome selects an intervention. The frozen
primitives, interpreter and four-input heuristic contract remain in force.

## Diagnosis and hypotheses

Across the original FULL development records, each seed retained the same six
TRAIN solutions through eight rounds and adopted no abstraction. The 144
heuristic slots contained only six distinct programs. All screens solved zero
of their four tasks; index-based ties sent both runtime-failing `head(nil)`
variants to all 48 full confirmations. This is a candidate-generation,
verification, memory and credit-assignment bottleneck. It does not establish
that a larger language or a lower acceptance threshold would fix learning.

H1: retaining the proposal frontier and verified rejection history increases
distinct, executable, candidate-dependent proposals under the same draw and
assessment ceilings. H2: learning a proposal-quality model from the improver's
own verified successes and failures improves the selection procedure beyond
static novelty. H3: useful heuristics survive full development confirmation and
independent task-family checks. Each hypothesis may fail.

## Fixed procedure

Seeds are 11, 22 and 33. Each seed starts from the same freshly executed original
one-round TRAIN learner. Its task grammar, library and recognizer are then held
fixed for three improver cycles to isolate changes to the improvement procedure.
Each arm owns its incumbent, proposal memory and learned model. No manual
library or heuristic AST is installed. All candidates come from the original
typed enumerator or its original seeded subtree mutation operation.

The arms are ORIGINAL (restart; first four enumerations plus two mutations),
STATIC (persistent frontier and verified novelty), and LEARNED (the same frontier
and novelty plus a NumPy proposal-quality model fit on preceding cycles). Every
arm draws 32 complete enumeration slots and two mutation slots per cycle. An
exhausted or failed draw remains a logged slot. Checkpoint replay enumerations
are recorded separately. At most six candidates are screened on the original
first four sorted VALIDATION tasks at budget 16, and at most two are confirmed
on all twelve original VALIDATION tasks at budget 64. AST size 12, expansion
limit 20,000, interpreter steps 2,000 and all original task budgets are unchanged.
Screen ties preserve the proposer's selected order, so a learned ranking can
influence confirmation rather than being overwritten by raw enumeration order.

All raw candidates receive the same independent semantic-contract probes.
Record interpreter failures, non-integer results, constant-within-task scores,
duplicate ASTs and duplicate observed behavior. STATIC and LEARNED select only
runtime-valid, candidate-dependent, previously unselected ASTs. ORIGINAL ignores
probe labels during selection, retaining the failed-prefix control. These
conditions are observable tests, not proof of universal function equivalence.

The fixed proposal model uses production/AST features, 80 NumPy gradient steps
and L2 coefficient 0.001. Its label is verified executable, candidate-dependent
behavior. Only preceding-cycle labels fit the selection model. This is a
proposal-productivity proxy, not a task-solve or RSI success claim. Current-cycle
labels may enforce the common semantic eligibility check, never fit that cycle's
ranking model. Save fitted parameters and evidence so selection can be replayed.

A new task heuristic is retained only on strict improvement in full original
VALIDATION hidden-verified solved fraction, with no loss on the separate six-task
confirmation partition. Runtime-invalid or input-constant proposals cannot be
adopted even if the frozen queue exhibits an apparent constant-offset gain.
Incumbent and candidate are compared on the same tasks and search state. Counts,
budgets, failures, all screens and confirmations, probes, replay work and CPU are
reported; equal ceilings do not imply equal actual computation.

## Transfer, memory and claims

Fresh task identities come from the already retained external corpus. Exclude
every author-name family appearing anywhere in the original 60 tasks, including
the original held-out identities. Family is the metadata prefix before ` with `;
this is a coarse grouping, not proof of semantic independence. Shuffle the 26
remaining family names with seed 20261004: first six families supply one task
each for confirmation, next eight supply one each for reporting-only audit.
Select members by the same seeded generator without evaluating task difficulty.
Keep the first ten distinct published examples and the remaining hidden examples.
Commit the assignment before any new transfer measurement.

Confirmation labels may reject updates. The separate audit loader is used only
after all cycles and policies are frozen; audit outcomes never feed selection,
model training, memory rules or another cycle. Public-learning modules cannot
open or import that capability. Original TEST is never loaded by this study.

Failure history may persist. Cached evaluation outcomes are reused only within
the exact task examples, grammar/library/recognizer, heuristic, search limits and
budget scope. A changed scope must miss or reject the cache. Learned rules require
verifier evidence; no rule is preserved as an effective improvement on narrative
or unit-test success alone. Compare ORIGINAL versus STATIC for loop engineering,
and LEARNED versus STATIC for evidence that the improver improved its method.

Task-solve gains require hidden verification and no confirmation regression.
Proposal-productivity gains must be labeled as such and confirmed on fresh public
task-derived probe profiles. They do not meet the original recursive improvement
criteria. A positive RSI claim still requires cumulative task capability and
causal evidence that improved improvement procedures produce further gains.

The follow-up stops after three cycles or 7,200 aggregate CPU seconds, whichever
comes first; an incomplete comparison is reported as partial. At most three
workers, one NumPy thread each. Do not alter this protocol after the audit is
opened. Each cycle reports performance, clusters, bottleneck, previous-attempt
failure, intervention and mechanism, verification, regression risks, results,
keep/revert/revise decision and its updated evidence-backed rule.
